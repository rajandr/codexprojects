Main path · rollout enabled · new or existing reference locked

The key dependency: for a rollout-enabled request, IDR holds initial classification until DB Lending supplies the Input ID and bill reference and sets the request to Ready For Classification.

2 / What each status means—and what DB Lending does

Every polling result is handled individually. Document uploaded initializes the request. Later statuses go to HandleIDRStatus; Sent to Processing system starts data retrieval and population before the final completion updates.

These are distinct fields: IDR request status is owned by IDR; DB Lending IDR status tracks that progress; Bill Data Capture Status becomes User Input Required at the final step. On Sent to Processing system, DB Lending first sets its IDR Status to Fetching Data. Only after both IDR data calls and population succeed does it set IDR Status = Completed and Bill Data Capture Status = User Input Required. IDR’s own request status remains Sent to Processing system.

Polling reads current records. It may skip intermediate transitions unless the API provides history; delivery and ordering semantics are still to be defined.

Only unresolved decisions are listed here. Confirmed decisions are incorporated into the flow, status rules and technical specification.

Timezone

Choose the timezone and datetime format for UpdatedDateTime and fetch_records_after. Explicitly deferred.

Failed-record retry and polling cursor

Define automatic retry/recovery for durably captured failed records. Capture before checkpoint advancement is agreed; the retry policy remains explicitly deferred.

Missed IDR updates

Define detection and recovery for missed fire-and-forget IDR Status API updates. Delivery acknowledgment, retry or reconciliation remain open.

Polling operation

Cron runs every 10 seconds and uses a persistent checkpoint per polling scope. Define the first-run timestamp, pagination and safe timestamp-boundary implementation, duplicate/stale handling and whether intermediate history is required.

TF3 event contracts

Define API endpoints, methods, authentication and error contracts; Gemini payloads, IDR pickup scheduling and failure handling.

Remaining data and transport details

ADS integration

Define handoff transport/acknowledgment, schema and correlation for app.inputs, delivery/retry handling, and detailed maker–checker, screening, due diligence and N1 contracts. The business sequence and discrepancy branch are confirmed.

How the 10-second cron works · persistent polling checkpoint

The schedule and the checkpoint are different. Every 10 seconds is when DB Lending attempts a fetch. The checkpoint records how far IDR updates have been safely received. Never calculate fetch_records_after as “now minus 10 seconds.”

Persistent state in DB Lending

Keep one checkpoint per polling scope: product code plus a normalized branch-code list. A checkpoint must survive service restarts. Changes to that scope require an explicit starting-point decision.

Suggested checkpoint fieldPurpose
polling_scopeIdentifies the product and branch set being polled.
fetch_checkpointLast safely captured IDR checkpoint. Sent as fetch_records_after on the next call.
last_attempt_atOperational timestamp for the latest attempt; never used as the data-fetch checkpoint.
last_success_atOperational timestamp for the latest completed fetch/capture.

Run sequence

  1. Start every 10 seconds. Allow only one active fetch per polling scope, using a lock or lease. If the previous fetch is still running, skip this tick rather than overlap it.
  2. Read the saved checkpoint. Send product_code, branch_codes and fetch_records_after = saved fetch_checkpoint to IDR Dashboard API. The initial checkpoint for a new scope remains to be agreed.
  3. IDR returns eligible updates and next_checkpoint. IDR applies the current branch, product, rollout-enabled and UpdatedDateTime filters. IDR determines the checkpoint using its own data boundary, not DB Lending's clock.
  4. Receive the complete result window. If results are paginated, fetch every page for the same window before advancing the checkpoint. Pagination details remain open.
  5. Capture the results durably in DB Lending. Save enough of each returned record to process it after a restart. Persist the captured batch and its next_checkpoint together in one database transaction. An inbox/batch table is a suggested implementation; physical schema is not prescribed.
  6. Advance only after durable capture. Commit fetch_checkpoint = next_checkpoint together with the records. If fetching, validation or persistence fails, leave the saved checkpoint unchanged and log the failure.
  7. Process captured records independently. Route each status to its Action set. Skip and log unknown statuses. On Action set failure, roll back that record's local changes, retain its failure information, log it and continue with other records. Automatic retry policy remains open.
  8. Use the persisted checkpoint on the next tick. After a restart or delay, resume from this value. Retain pending/failed captured records for recovery; never equate fetching a record with successfully processing its Action set.
Advancement rule: the fetch checkpoint means “safely captured in DB Lending,” not “all Action sets succeeded.” This allows the fetch checkpoint to advance without dropping failed records. Durable capture must exist before enabling this behavior.

Example: a delayed run

The saved checkpoint is 10:00:00. DB Lending is delayed and next runs at 10:00:35. It still requests updates after 10:00:00. If IDR returns next_checkpoint 10:00:34, DB Lending stores the complete results and that checkpoint together. The following request starts after 10:00:34. Times are illustrative; timezone remains open.

Failure and boundary rules

  • API timeout or incomplete pages: retain the old checkpoint; fetch again on the next run.
  • Database failure during capture: roll back the captured batch and checkpoint together.
  • Crash after capture: the saved records remain available even though the checkpoint has advanced.
  • Empty results: advance only if IDR explicitly returns a valid next_checkpoint certifying the completed window; never substitute local time.
  • Same UpdatedDateTime: IDR must not advance past a timestamp while eligible records at that timestamp remain uncaptured. A page's maximum timestamp alone is not a safe checkpoint. Stable window/pagination and transaction-visibility semantics must be defined to prevent omissions.
  • Repeated or stale records: define deduplication and ordering checks before processing so initialization is not repeated and a newer status is not overwritten. The exact key/revision strategy remains open.

The agreed request filter remains UpdatedDateTime > fetch_records_after. next_checkpoint is an IDR-issued datetime through which the complete eligible update window has been returned; its production implementation must make that promise safe. Checkpoint boundaries, initial value, timezone and automatic failed-record retries remain open. Current rollout filtering still applies: disabled records stop being returned, including in-progress records.

Dashboard eligibility · resolved

Match the supplied branch-code list, product code and UpdatedDateTime > fetch_records_after filter. For each candidate request, derive product from Parent Ref characters 1–2 and class from character 3. Return it only if a config row matches branch + product + class with enabled_flag = Yes. A disabled or absent config match is excluded. Evaluate the current rollout configuration on every poll: disabling it stops returning records immediately, including in-progress requests. DB Lending retains its last received status; disabling rollout does not imply cancellation in IDR.
